## 0. Executive decision

The proposed identity:

> TITMAS is an adaptive immune capability for complex digital ecosystems,
> not a control plane, asset owner, or replacement platform.

is consistent with the existing governance system only when “adaptive immune
capability” is defined as:

- a distributed, cross-component capability pattern;
- a strategic identity and review constraint;
- source-bound and Evidence-aware;
- limited to sensing, understanding, risk indication, Attention support,
  feedback, and Human Decision support;
- non-owning, non-custodial, non-authoritative, and non-executing by default.

It must not be defined as:

- a new Runtime;
- an architecture layer;
- a central immune service;
- a mandatory pipeline;
- an Agent supervisor;
- an external-service controller;
- a universal Health, Evidence, Permission, or Truth system.

The correct project-level placement already exists:

```text
architecture/titmas-architecture-charter-v0.1.md
```

That Charter explicitly governs TITMAS mission, responsibilities,
non-responsibilities, Authority boundaries, interoperability principles,
staged routes, and stop conditions. Creating another “TITMAS Project
Constitution” would duplicate authority and create precedence ambiguity.

Decision:

```text
IMMUNE_IDENTITY_AS_PROJECT_STRATEGIC_IDENTITY=PASS
IMMUNE_IDENTITY_AS_NEW_COMPONENT=BLOCK
IMMUNE_IDENTITY_AS_CONTROL_PLANE=BLOCK
SECOND_TITMAS_PROJECT_CONSTITUTION=BLOCK
PROJECT_CHARTER_REVISION=HUMAN_DECISION_REQUIRED
```

This review does not modify the Charter or authorize its revision.

## 3. Immune Identity alignment review

### 3.1 Ecological Self-Limitation

Status: `PASS`

The identity reinforces Ecological Self-Limitation when TITMAS is a capability
emerging from limited actors rather than a controller above them.

```text
IMMUNE_CAPABILITY_NE_IMMUNE_CENTER=true
COMPOSITION_NE_AUTHORITY_AGGREGATION=true
SENSING_NE_CONTROL=true
ADAPTATION_NE_AUTOMATIC_EXECUTION=true
```

Conflict occurs if “immune system” is used to justify:

- global visibility by default;
- mandatory integration;
- continuous surveillance;
- automatic quarantine;
- universal shutdown;
- external-service writeback;
- a single global Health or Trust score.

### 3.2 Evidence First

Status: `PASS_WITH_NON_ELEVATION`

Immune sensing may create:

- source-bound observation;
- a candidate event;
- a Health finding;
- an Attention Candidate;
- a request for further Evidence.

It does not automatically create:

- admitted Evidence;
- Truth;
- causality;
- verification;
- Permission;
- a decision.

```text
SENSOR_OUTPUT=OBSERVATION_MATERIAL
OBSERVATION_NE_EVIDENCE=true
EVIDENCE_NE_TRUTH=true
IMMUNE_ALERT_NE_DECISION=true
```

### 3.3 Authority Separation

Status: `PASS_WITH_ROLE_SEPARATION`

The identity fits the established sequence:

```text
Observe
  -> preserve source and limitation
    -> package / validate when applicable
      -> evaluate and recommend
        -> explicit Human Decision
          -> separately authorized execution
            -> new observation and review
```

TITMAS does not gain Observation, Evaluation, Authorization, and Execution
authority merely because the immune metaphor includes all these stages.

### 3.4 Interface Boundary

Status: `PASS_IF_EXISTING_COMPONENT_ROLES_REMAIN`

| Existing boundary | Immune contribution | Prohibited elevation |
|---|---|---|
| Native external source | Source-specific observation | TITMAS ownership |
| Agent Evidence | Capture/package/validate candidate | DBOS admission, Truth |
| Agent Health | Scoped repository-health diagnosis | Runtime monitor, automatic fix |
| DBOS | Applicable canonical identity/execution/evidence/lifecycle boundary | Universal immune database |
| SAEE | Protected bounded evaluation/recommendation | Command, writeback, public immune core |
| TITMAS Situational View | Attention-oriented source projection | Control panel, Truth source |
| Human Authority | Explicit scoped decision | Automatic execution |
| Codex/Agent executor | Executes only an authorized task | Self-expanding authority |

The Immune Identity must not create a new row in the Core Component
Responsibility Map.

```text
NEW_CORE_COMPONENT_REQUIRED=false
NEW_INTERFACE_REQUIRED=false
NEW_DATA_FLOW_REQUIRED=false
```

### 3.5 No Duplicate Component

Status: `PASS_ONLY_AS_IDENTITY_AND_REVIEW_RULE`

The principle is beneficial when it prevents TITMAS from duplicating:

- GitHub;
- Agent frameworks;
- Agent Health;
- Agent Evidence;
- DBOS;
- SAEE;
- external deployment, backend, planning, knowledge, or security services.

It violates the principle if it leads to:

- `titmas-immune-core`;
- a universal sensor service;
- an immune event database;
- a global immune controller;
- a new Health engine;
- a new Agent quarantine service;
- a replacement for existing provider alerts or monitoring.

## 5. Immune Model review

### 5.1 Simplified model

The proposed model is useful as a human explanation:

```text
Digital Ecosystem
  -> Sensing
    -> Evidence-aware preservation
      -> Health diagnosis / evaluation
        -> Human Attention
          -> Human Decision
            -> Authorized adaptation
              -> New observation
```

### 5.2 Non-pipeline warning

It must not be treated as a mandatory Runtime pipeline.

Not every observation:

- becomes Evidence;
- requires Agent Health;
- enters DBOS;
- is eligible for SAEE;
- appears in Attention;
- requires a decision;
- results in adaptation.

More precise distributed paths:

```text
Native source
  -> source-bound observation
     ├─ optional Agent Evidence candidate / validation
     │    -> optional applicable DBOS admission
     ├─ optional Agent Health scoped diagnosis
     ├─ optional approved SAEE evaluation from eligible input
     └─ optional reference-only Attention projection
              -> Human Decision when required
                   -> separately authorized executor
                        -> result and new observation
```

### 5.3 Stage semantics

| Immune metaphor | Safe TITMAS meaning | Must not mean |
|---|---|---|
| Sensor | Native source or bounded observation method | Continuous universal surveillance |
| Evidence | Source-preserving candidate/admitted record under existing boundary | Every log or alert is Truth |
| Health diagnosis | Agent Health scoped finding or another source-owned diagnosis | Global organism score |
| Evaluation | Approved bounded SAEE or domain evaluation | Automatic decision |
| Attention | Human Attention Amplification | Agent routing or Permission |
| Human Decision | Explicit scoped Authority | Central machine decision |
| Adaptation | Separately authorized change and feedback | Automatic mutation, quarantine, shutdown |
| Immune memory | Source-bound history and explicit continuity | New central TITMAS memory database |

## 8. TITMAS Drift Check review

### 8.1 Classification

Status: `ACCEPT_AS_PROJECT_REVIEW_GATE`

The Drift Check is:

- a question set;
- a post-task review obligation;
- a stop/escalate mechanism;
- an Agent-readable identity reminder.

It is not:

- a Runtime;
- a policy engine;
- an automatic enforcement component;
- a repository hook;
- an authorization service;
- a substitute for Human Review.

### 8.2 Recommended question set

```text
TITMAS_IDENTITY_CHECK

1. Does this work strengthen bounded ecosystem immune capability?
2. Does it add control over an Agent, asset, repository, or external service?
3. Does it duplicate or replace an existing external tool or project?
4. Does it create a new canonical Truth source or shadow state?
5. Does it create or aggregate Permission, identity, or automatic decision power?
6. Does it create a new component, architecture layer, mandatory gateway, or Runtime?
7. Does it increase integration or maintenance burden?
8. Does it preserve canonical source, owner, freshness, limitations, and Human Authority?
9. Is there direct Evidence that it lowers one-person management cost, or only a theory?
```

### 8.3 Result states

```text
PASS
REVIEW_REQUIRED
STOP_AND_ESCALATE
```

`STOP_AND_ESCALATE` is required when any of the following is true:

```text
CONTROL_ADDED=true
REPLACEMENT_CREATED=true
NEW_TRUTH_SOURCE_CREATED=true
PERMISSION_AGGREGATED=true
AUTOMATIC_DECISION_OR_EXECUTION_ADDED=true
MANDATORY_GATEWAY_CREATED=true
CANONICAL_SOURCE_OR_OWNER_UNKNOWN=true
```

“Stop” means:

- do not advance the proposal to the next governance or implementation gate;
- preserve the source and reason;
- request Human Review.

It does not mean automatically:

- stop an Agent;
- shut down a service;
- revoke Permission;
- roll back a repository;
- modify an external system.

### 8.4 Placement

If adopted:

1. The normative obligation belongs in the project-level TITMAS Architecture
   Charter's review/change/stop section.
2. `AGENTS.md` may contain a short derivative checklist that cites the
   canonical Charter clause.
3. The derivative checklist must not redefine or expand the Charter.

## 9. Can the principle prevent future drift?

Decision: `REDUCES_RISK_BUT_DOES_NOT_GUARANTEE_PREVENTION`

The principle can improve:

- identity recall;
- early detection;
- negative-boundary review;
- duplicate-component detection;
- source/Authority checks;
- stop-and-escalate consistency;
- decision traceability.

It cannot guarantee prevention because:

- future humans can revise or ignore the Charter;
- project incentives can favor platform expansion;
- external ecosystems can change;
- metaphors can be reinterpreted;
- an Agent checklist cannot exercise Human Authority;
- no control plane exists to block every action;
- a document does not prove operational compliance.

```text
DRIFT_PREVENTION_GUARANTEED=false
DRIFT_DETECTION_SUPPORT=true
DRIFT_STOP_ESCALATION_SUPPORT=true
HUMAN_ENFORCEMENT_REQUIRED=true
```

The principle prevents semantic drift only when future decisions:

- cite the Charter version;
- complete the Drift Check;
- retain negative results;
- stop on blocked conditions;
- receive explicit Human disposition;
- do not treat recommendation as authorization.
